# Recovery review and validation

The bounded code review covered `backend/jobs.py`, `backend/recovery.py`, `backend/worker.py` and `packaging/macos/Launcher.swift`. It identified two concurrency bugs before final validation:

- An exception between native process launch and entry to the cleanup block could leave an engine alive after the supervisor reported a terminal status. The complete launch/PID registration/stdin sequence is now protected by cleanup; the MD worker's SIGTERM handler requests cooperative cancellation, and terminal jobs are checked for a surviving native engine before recovery.
- An unsynchronized stale status poll could overwrite a newly resumed worker's PID and restart history. Poll transitions now share the submit/resume/cancel lock and recheck the on-disk status generation before saving a dead-worker transition.

The reviewer reproduced the original failures with small deterministic mocks, then reran those reproductions against the fixes: the native child is stopped and reaped, the replacement PID/restart history remain intact, and terminal jobs with surviving engines enter cancellation rather than resume. No further actionable issues were found in that bounded review. This was an assistant code review, not independent scientific validation or a proof that all failure interleavings are covered.

`backend/tests/test_recovery.py` additionally checks parameter/System/integrator/configuration and saved-frame corruption, changed native runtime, missing checkpoints, repeated Stop, output-identity reuse after an injected result-conversion failure, and the reviewed concurrency cases. Real native interruption/stop/restart evidence is recorded separately in `recovery-native.json` and generated by `scripts/check_recovery.py` using an isolated data directory.

The Swift launcher passes `swiftc -typecheck`. Native menu clicks still require an unlocked desktop/manual GUI check; compilation does not verify their appearance or behavior in an actual menu interaction.

A final integration review verified that concurrent downloads own distinct immutable ZIPs, and Resume waits for ZIP construction without waiting for the completed snapshot to finish streaming. It also found that Starlette skips background cleanup on rejected Range requests and disconnected sends. `TemporaryFileResponse` now unlinks its owned snapshot in `finally`, and all six download regressions pass. The helper is used by job and project exports.

Resource admission is shared between readiness and submission through `backend/resources.py`. HTTP regression tests verify atom, coordinate and disk-space blockers cannot be bypassed by posting directly to `/api/jobs`, and that validation/rejection do not change stored inputs or create jobs. The real browser recovery check additionally confirms readiness suspends during activity and rechecks after completion.

The broad native browser audit found a startup Stop race: SIGTERM can terminate an interpreter before its cancellation handler is installed, and the supervisor had classified every worker exit as interrupted. A retained `cancel.request` now produces `cancelled` once both worker and native child have exited; absence of that explicit request still produces `interrupted`. A surviving native engine keeps the job in `cancelling` and Resume remains blocked. Six added regressions cover all worker kinds, unexpected exits, and native orphan shutdown. Repeated real startup checks are recorded in `cancellation-startup.json`, and the latest browser recovery run still completes 500 OpenMM steps after Stop and Resume.
